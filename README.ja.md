# bmo-calendar

プラットフォームの日付付きイベントをひとつのサービスで扱います。カレンダーとイベントは brain サービスにメモリとして
保存され(brain がマスターで、このユニットはその従属です)、互いに分離された二つの領域、つまり各アカウント自身の領域と
その会社の組織領域に分けて保持されます。繰り返しイベントは発生 1 回につき 1 行で返します。アラームは期日になると
receiver を通じて supervisor に一度だけ通知します。会社の会議室などのリソースを予約でき、同じリソースの二つの予約が
重なることはありません。個人の Outlook カレンダーの 1 日分を、本人の PC 上で本人の BMO のために読み取ります。さらに、
これらをサイドバー項目の下に表示するコンソールバンドルも含みます。
`docs/design.md` はこのサービスが何であるかを、`docs/api.md` はその境界を記述しています。すべてのルート、発行する
イベント、配置するツール、呼び出す先、設定がそこにまとめられています。他のユニットにはすべてそれぞれの API を通じて
アクセスします。

## テスト

`cargo test`(testbed 経由で実行)は、このクレート唯一のハーネスである `tests/main.rs` を実行します。brain、
receiver、アカウントサービス、agency、ノードサービス、Teams ページサービス、Microsoft Graph のスタンドインを
ループバックポート上に立て、次の内容を検証します。初回の読み取りで作成され領域ごとに保持されるカレンダー
(`calendars.rs`)、管理者が個人の領域を読めるがそこでは何も書かず何も作らないこと(`administrator.rs`)、各会社の
領域はその会社の人と管理者だけが読め、他社の領域への管理者の書き込みは拒否され、ツールセッションの保持者がその
所有者のアカウントとして振る舞い、会社への一度きりの移行が行われること(`companies.rs`)、リソースと予約、重複の
拒否、承認とその通知(`bookings.rs`)、二つの予約が重なるかどうか(`overlap.rs`)、受信したスケジュールがその会社に
保持されること(`schedules.rs`)、ラベル付きでの書き込み・変更・キャンセル、id による冪等性、ドキュメントどおりの拒否、
brain のストリームによる更新(`events.rs`)、期間内に展開される繰り返しイベントと 1 回分だけの変更やキャンセル
(`repeats.rs`)、期日のアラームを一度だけ通知し、遅れたものは遅延とともに通知し、再起動をまたいでも二度通知せず、
それぞれのアカウントが届く部屋に通知するビート(`alarms.rs`)、起動中の Outlook または Graph から本人のノード上で
読む個人の Outlook の 1 日分、本人のものでないノードへの拒否、業務コード形式として読むタイトル(`outlook.rs`)、
コンソールのガード、bmo-ui 自身の契約の読み方で読んだコンソール画面のマニフェストとそのイベント(`console.rs`)、
OpenAPI ドキュメント(`openapi.rs`)、そしてリポジトリ自身のチェック(`repository.rs`)です。ツールのクレートは、
スタンドインのカレンダーサービスを相手にする独自のハーネス `tools/calendar/tests/main.rs` を持ちます。コンソール
バンドルのチェックは `client/` 内で実行する `bun run check` です。

## 画面チェック

コンソールバンドルの画面は、コンソールや稼働中のユニットなしにブラウザで動かします。

1. `cargo test --test main preview -- --ignored --nocapture` は、会社の会議室・予約・組織イベントを含むテスト用
   スタンドインの上でサービスを起動し、応答するアドレスを表示して、停止されるまで動き続けます。
2. `client/preview/` で `PREVIEW_SERVICE=<that address> PREVIEW_KEY=<account> PREVIEW_ROLE=<member or
   administrator> bun x nuxi dev --port <port>` を実行すると、その上で画面を Nuxt アプリとして配信します。
   クライアントはレイヤーとして組み込まれ、バンドルの文言がインストールされ、relay 呼び出しはコンソールの認証情報と
   その閲覧者のキーとロールでプロキシされます。スタンドインのアカウントは、オーナー `1`(会社 `10`)、メンバー
   `2`(その会社の責任者)、メンバー `3`(承認待ちの会議室の管理者)、メンバー `4`(別の会社)、`5`(所属なし)です。
3. ブラウザドライバが画面のアクセシビリティスナップショットを読み、デスクトップ幅とスマートフォン幅(360×780)で
   ページ内の寸法を測定します。

チェックで測定する内容は、コンソールバンドルのブラウザテスト `client/tests/browser/`(`client/package.json` の
`bmo.browser` で宣言され、testbed が実行)に保持されています。コンソールやサービスを介さずに画面をひとつの
ハーネスページにまとめ、実際のブラウザでデスクトップ幅と Galaxy S25 の幅(412×915)で開き、スタンドインが
プラットフォーム管理者に対するのと同じようにサービスの代わりに応答します。

## 構成

| フォルダ | 内容 |
|---|---|
| `src/` | サービスとそのコマンド:ルート、各領域の brain のキャッシュ、会社と会社への移行、リソースと予約、アラームとビート、通知済みマークのストア、個人の Outlook の 1 日分とそれをノード上で読む PowerShell コマンド、コンソール画面の宣言、OpenAPI ドキュメント |
| `tools/` | デプロイがツールホストに配置するカレンダーツール:クレート、マニフェスト、入力スキーマ、マニュアル |
| `client/` | コンソールプラグインのバンドル(独立したプロジェクト) |
| `deploy/` | サービスのユーザーユニット |
| `docs/` | サービスが何であるかとその境界の正式な記述、および OpenAPI ドキュメント |
| `tests/` | クレート唯一のテストハーネスと、それが使うスタンドイン |

ルートには Cargo マニフェスト、`Cargo.lock`、`testbed.toml`、`install.toml`、`rustfmt.toml`、`settings.toml`(バイナリに
組み込まれる既定値)、`CLAUDE.md`、`PERSONAL-DATA.md`、`LICENSE` があります。

## コマンド

- `bmo-calendar serve` は brain を読み、1 分ごとにビートを回し、停止されるまでルートに応答します。
- `bmo-calendar health` は、設定で指定されたサービスが ready と応答すれば 0 で終了します。
- `bmo-calendar openapi` は OpenAPI ドキュメントを出力します。同じものが `docs/openapi.json` にあります。
- `bmo-calendar tool-env` は、ツールがサービスを見つけるためのデータルートの `env/calendar.env` を書き出します。

設定は、バイナリに組み込まれた `settings.toml`、次にリリースの隣にあるデプロイの `settings.toml` と
`settings.local.toml`(データルートの `env/calendar.toml`)、最後に環境変数 `BMO_CALENDAR_<TABLE>__<KEY>` の順に
読み込まれます(`docs/api.md`、「Settings」)。
